# iPad 6 安装、汉化与触摸排障记录

记录日期：2026-11-01 至 2026-11-02。目标是把一次成功安装中可复用的做法固化为中文默认值，同时保留故障处理过程和验证边界。设备身份标识、IP 分配记录、凭据、固件和原始设备日志不属于公开记录。

## 1. 方案和设备

实测设备是 iPad 6 Wi-Fi，型号 `iPad7,5`，板型 J71b，128 GB，原系统 iPadOS 17.7.10。安装的是 Omarchy A v0.2.0，而非把标准 PC Omarchy ISO 写入 iPad，也不是 LinuxRunner 的应用内 Linux。

电脑通过 Lightning 数据线连接。Omarchy A 安装后保留 iPadOS；Linux 冷启动仍依靠电脑和 Orchard。用户最终选择将较多空间留给 Linux；这一偏好没有被编码成自动分区默认值。

## 2. DFU 和 Resize APFS

- “连接电脑”的画面表示恢复模式，不能把它当成 DFU 成功。
- USB-C 转 Lightning 线进入 DFU 不可靠，换成 USB-A 转 Lightning 后继续。
- 进入 DFU 后发生过重新连接超时；在尚未写分区时，拔下 iPad 端插头，等待约 2 秒后接回，再继续启动。
- 看到 `Booting Kernel` 后回到 iPadOS 主屏幕，解锁并启动 Resize APFS。
- Resize APFS 曾一点就闪退。检查发现当时的 Python ZIP 解压没有保留 app 主程序的执行权限（变成 `0644`）。重新用 macOS `ditto` 解压，确认可执行权限后重建启动覆盖层，app 才正常启动。不要把“所有 app 文件都 chmod 755”当成通用修复。
- 先清理 iPadOS 存储，再调整 APFS。界面从约 108.3 GB allocated 降到约 64 GB allocated；最终将 APFS 设置为约 72 GB，留下约 56 GB unallocated。
- 等待 **Completed and verified** 后才继续安装。此次没有保存足以精确计算 APFS 搬移耗时的起止记录，不能事后编造用时。

## 3. 安装和启动

通过发布版 Orchard 安装器完成恢复环境引导、分区选择、系统写入和首次启动。Linux 空间中约 1 GiB 为 VFAT 启动分区，约 51.2 GiB 为 ext4 根分区；GB 与 GiB 不同，不能直接把界面上的 56 GB 当作 56 GiB。系统空闲空间约 47 GiB。

本次安装回执的安装阶段约 153 秒；包含启动过程的记录约 274 秒。这不包括 APFS 调整、固件下载、手工 DFU 重试和之后的汉化。

安装时在本地私密提示中设置账户密码和 6 位 PIN。SSH 使用安装器导入的公钥，Dropbear 关闭密码登录。USB SSH 的一般用法见[中文指南](README.md#日常使用)。

冷启动使用 `orchard launch`，不能配置成脱离电脑自动原生引导。

## 4. 横屏和输入法

第一次将显示输出旋转到 `90`，并保存到 Labwc 自启。后来排查触摸时临时切回竖屏。最终验证横屏点击和 PIN 解锁正常后才恢复横屏并保存。

安装的软件包：

```text
fcitx5
fcitx5-chinese-addons
fcitx5-gtk
fcitx5-qt
fcitx5-configtool
noto-fonts-cjk
```

默认镜像直接包含这些包。人工补装时，CJK 字体下载较大；此次使用 USTC 的 Arch Linux ARM 镜像下载，并按包数据库 SHA-256 核对后放入 pacman 缓存。没有绕过 HTTPS 证书检查。版本号、单次包校验值和缓存路径没有写成未来默认依赖。

生成 `zh_CN.UTF-8`，将系统 locale 设为中文。Labwc 和 systemd 用户环境设置：

```ini
LANG=zh_CN.UTF-8
LANGUAGE=zh_CN:zh:en
XMODIFIERS=@im=fcitx
GTK_IM_MODULE=fcitx
QT_IM_MODULE=fcitx
```

Fcitx5 profile 包含 `keyboard-us` 和 `pinyin`，默认拼音。启动命令是 `fcitx5 -d`；曾误用 `--daemon`，只显示帮助，已修正。中文切换默认热键为 `Ctrl + 空格`，另提供“切换中英文输入”应用入口。

中文 Shell 词典覆盖这版全部 572 个英文 key，并核对 `%1` 等占位符。菜单另读 `menu.json`，只安装 `shell.json` 会留下英文菜单。中文词典以 Omarchy 上游中文翻译为基础，补齐本版缺失项目；随源码提交，运行时不在线下载。

安装字体前就运行的 Qt 桌面仍可能显示方框。此次是在已正常解锁的会话里重启 Shell 后才正常显示中文；没有终止锁定中的 Shell 来绕过认证。新镜像先安装字体，再启动 greeter、桌面和输入法，避免首次使用遇到这一顺序问题。

## 5. 触摸故障与恢复顺序

故障最初表现为锁屏数字完全点不动；在 iPad 本机玻璃屏幕轻点，而不是在 Mac 预览窗口中点。

1. 检查屏幕是否只是熄灭；用正常唤醒操作点亮面板，锁屏继续保持安全状态。
2. 只统计输入事件，不记录 PIN。最初触摸设备没有上报事件，单纯切方向无效。
3. 经设备型号、驱动绑定及固件名检查后，只重新初始化 J71b 的 Apple Z2 触摸控制器。随后再次监测能收到触摸事件，说明驱动恢复。
4. 此时曾启用过 `mouseEmulation="yes"` 兼容模式。桌面窗口可以拖动，Qt 顶栏和锁屏却不能正常点击。
5. 通过本地 Mac 终端隐藏输入 PIN，并经 SSH 标准输入传给虚拟键盘，走正常 PAM 验证解锁。PIN 没有作为进程命令行参数或日志保存，也没有取消锁屏认证。
6. 恢复原生触摸 `mouseEmulation="no"`，并将命名触摸设备映射到实际显示输出。顶部菜单恢复点击。
7. 横屏下额外加入的两个相反方向旋转矩阵都没有正确工作。撤销额外旋转，用两个可见目标测量：在正常校准矩阵下，两个实际触点都落在对应目标附近，说明不应再叠加旋转。
8. 保存横屏、保留原生触摸及输出映射。最后在 iPad 本机点击锁屏数字，用 PIN 正常解锁，验证原问题解决。

最终原则是 **输出旋转、触摸映射只各做一次**。不把失败的兼容模式或旋转矩阵作为默认值。当前 fork 已有 `touch-output` 动态映射和旋转监听，应复用它们，而不是再硬编码 J71b 之外设备的连接器名。

### 触摸完全无事件时的维护操作

以下是此次使用过的 J71b 专用操作，需在还能通过 SSH 连接时由维护者手动执行；不是开机服务、不是默认自愈脚本，也不能用于其他机型。先确认没有进行磁盘写入或系统更新。

```sh
sudo bash <<'ROOT'
set -euo pipefail
driver=/sys/bus/spi/drivers/apple-z2
device=/sys/bus/spi/devices/spi0.0
test "$(readlink -f "$device/driver")" = "$driver"
firmware=$(tr -d '\000' < "$device/of_node/firmware-name")
case "$firmware" in apple/j71b-*) ;; *) echo 'Not the verified J71b touchscreen' >&2; exit 1;; esac
test -r "/lib/firmware/$firmware"
printf 'spi0.0' > "$driver/unbind"
sleep 1
printf 'spi0.0' > "$driver/bind"
udevadm settle --timeout=15
ROOT
```

驱动故障属于 Orchard 的硬件支持范围；本 fork 记录处理方法，不携带用户固件、不自动执行上述重置。

安装初期 iPadOS 截图服务因缺少匹配的开发者映像未能工作；当时通过 QuickTime 的 USB 画面预览查看设备。Linux 启动后直接使用 Wayland 截图，不依赖 Mac 预览窗口控制触摸：

```sh
XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-0 grim -s 0.5 screenshot.png
```

运行在当前图形会话用户中；运行目录和 Wayland socket 应以实际会话为准。半尺寸截图能减少 SSH 传输量。个人截图、浏览器画面和原始日志不随公开源码提交。

- Fcitx5 拼音出现候选词，实际提交并读回“你好”。

这些是现有已安装系统上的结果，不应写成“当前 main 新构建镜像已完成硬件验收”。新构建仍需要单独验收安装、greeter、桌面和冷启动。

## 7. 触摸复发补记（2026-11-02）

在上述短时点按和 PIN 回归验证通过后，用户再次报告无法点击。初检时锁屏已熄灭；点亮屏幕后，用户确认数字仍无反应，说明不能只解释为未唤醒。

此时系统和 SSH 正常，原生触摸、显示输出映射、横屏及正常校准矩阵没有改变。IRQ 和 SPI 传输计数仍在增长，SPI 错误计数为 0；这些只能说明传输链路仍有活动，不能证明触摸报告有效。监测窗口里没有收到输入事件，但空闲时没有事件也不能单独证明硬件失效。

用户在 Mac 终端隐藏输入 Linux 管理员密码后，手动执行了上述针对 J71b 的驱动解绑、绑定。日志确认控制器重新初始化，输入设备重新注册，之后用户报告点击恢复，系统也确认正常解锁。恢复过程没有修改中文配置或方向设置。

**当前结论：这是一次可恢复但会复发的触摸链路故障，具体根因尚未定位。** 驱动重新绑定既会重启控制器，也会重建上层输入设备，因此不能仅凭恢复就断定是固件、驱动或桌面输入状态中的某一层。熄屏/唤醒是否为触发条件仍待对照复现。

此操作属于临时恢复方法，不是永久修复；之前的“验证通过”只说明当时的短时测试通过。后续需记录复发条件、比较内核侧与桌面侧事件，并覆盖多次熄屏/唤醒及长时间空闲，再认定稳定性问题已解决。本 fork 不因此新增反复重置控制器的后台服务，也不将其他机型的驱动恢复补丁直接套用到 J71b。

## 8. J71b 驱动候选补丁与上游评审（2026-11-02）

候选补丁已提交到 Orchard 上游草稿 [PR #52](https://github.com/OrchardLinux/orchard/pull/52)，源码分支为 [jarodlee/orchard:fix/j71b-runtime-recovery](https://github.com/jarodlee/orchard/tree/fix/j71b-runtime-recovery)。它参考了上游 [issue #24](https://github.com/OrchardLinux/orchard/issues/24) 描述的持续控制回复、没有触摸报告这一故障特征；本机此前的中断和输入计数与之相符，但尚未证明是同一根因。

补丁只在 J71b 的驱动匹配数据中启用：报告初始化完成后，连续控制回复达到 64 次、持续至少 2 秒且相邻间隔不超过 250 毫秒时，释放残留触点并在工作队列中重新启动控制器。正常帧、空队列及其他回复会清除检测计数；单次恢复中的启动失败最多尝试 3 次。其他机型沿用原有路径。这不是中文桌面配置，也不是定时重置脚本。

本次验证：

- Orchard 完整内核构建成功，使用 apple-16k 冻结配置和 Debian Clang 19.1.7。
- 447 项单元测试通过，包括 9 项编译并执行实际新增 C 函数的合成故障测试；Linux 补丁风格检查无错误、无警告。
- 在已安装的 v0.2.0 系统上临时卸载旧模块并加载候选 `apple_z2.ko`，驱动绑定及触摸输入设备注册成功。
- 用户在 iPad 本机完成 PIN 解锁、打开应用菜单及拖动窗口，确认点击准确。
- 完成一次锁屏、熄屏 5 秒、唤醒测试，用户再次确认 PIN 点击及解锁正常；未发现异常恢复日志，SPI 错误计数为 0。

**当前状态仍为候选补丁，尚未验证真实长期故障发生后的自动恢复。** 还需覆盖长时间空闲、较长熄屏，以及控制器启动成功后仍再次失灵时是否会循环重启。草稿 PR 明确保留这些待验证项，不将短时测试写成永久修复已经生效。

本机目前仅在内存中加载候选模块，原来的磁盘模块未被覆盖，重启会恢复使用原模块。上游尚未合并，此 fork 的发行镜像和中文默认配置也未自动启用该候选补丁。测试脚本、设备原始日志、固件、校准数据和认证信息不随公开文档上传。

## 9. 从电脑改接墙充后没有充电（2026-11-02）

用户将 USB-C 转 Lightning 线直接接到 20W 墙充后，系统仍报告 `lightning/online=1`、`usb_type=SDP`、`input_current_limit=500000`，电池为 `Discharging`。USB 控制器保留 `configured` 状态，允许电流 `current_max=2000`（单位微安，即 2 mA）。这些是驱动接口读数，不代表充电头只有这个功率，也不能把 500 mA 限流当成实测充电电流。

处理经过：

1. 保持 Wi-Fi SSH 连接，锁屏熄屏降低耗电。电池净放电电流随后从约 1.7 A 降至约 0.07 A，仍未充电。
2. 物理拔插一次后仍未恢复。用户在 Mac 终端隐藏输入 Linux 管理员密码，临时解绑、重绑已有的 configfs USB gadget `linux-recovery`，清除旧 USB 会话；脚本设置超时并保留重绑恢复步骤。
3. 会话清除后，USB 状态变为 `not attached`，电源类型为 `Unknown`，仍只允许 500 mA。此步骤本身尚未恢复充电。
4. 用户将 iPad 端 Lightning 插头翻面并重新接回同一个 20W USB-C 墙充。驱动随后识别为 `BrickID`，`current_max` 和 `input_current_limit` 都变为 2400000（2.4 A）。连续三次采样中，电池均为 `Charging`，净充入电流约 1.59–1.60 A，电压约 3.72 V，温度约 34°C。

这次验证说明充电已恢复，但 USB 会话重建、重新插拔及插头方向都参与了过程，尚不能单独认定哪一个因素是根因，也不将此过程设成开机自动操作。保留现有驱动的电源识别和限流策略，未强写充电电流或绕过保护。这与触摸补丁 PR #52 是两个独立问题。

当时电池百分比仍为 0%，`health` 标记先后出现 `Overheat`、`Dead`，与温度、剩余电荷和正向充电电流读数不一致。这些读数需另行核对，不能仅凭该健康标记认定电池损坏，也不能因已恢复充电便声称电量显示问题已解决。

后续电量读数曾升至 7%，但继续亮屏测试时，已识别的墙充仍出现限流回到 500 mA、电池再次放电的情况，电量回落至 2%。将亮度暂降至 30% 后，连续采样恢复为小电流充电（约 59–67 mA）。因此，“恢复充电”只描述当时验证结果，充电稳定性仍未解决；需先减少耗电、补充电量，再单独排查限流回落。未强制提高充电电流，也未把这次亮度调整设为中文用户的默认值。

## 10. 点击正常但窗口无法拖动（2026-11-02）

后续用户报告点击正常，按住窗口标题栏却无法移动窗口。另开未最大化的普通终端后也能复现，因此不能只解释为浏览器标签栏的特殊行为。

排查及恢复过程：

1. 确认仍使用原生触摸、命名设备输出映射和单位校准矩阵。内核未记录控制回复卡死或自动恢复。
2. 只统计输入事件代码和次数，不保存坐标、触点 ID 或 PIN。用户拖动时可见连续的 X/Y 更新及成对的按下、松开，说明移动事件仍在上报。
3. 临时改成标题栏按下即移动，无效后恢复原配置；重启屏幕键盘和多指按下后全部抬起也没有恢复拖动。这些尝试均未作为默认配置保留。
4. 用受解锁状态检查保护的软件鼠标及 GTK 诊断窗口交叉测试。软件鼠标能移动窗口；物理触摸仍不能，且诊断窗口报告修饰键为 0。问题缩小到桌面的触摸拖动处理，尚不能只凭这些测试认定具体根因。
5. 用户保存内容并明确同意后，结束桌面 `labwc` 会话，由 `greetd` 回到正常登录界面。应用窗口会关闭；Linux 和内存中加载的候选触摸模块仍保留。
6. 登录界面当时也无法触摸。检查其独立配置 `/usr/share/omarchy-greeter/labwc/rc.xml`，发现没有桌面的命名触摸映射。用户在 Mac 终端隐藏输入 Linux 管理员密码后，维护脚本读取 greeter 当前启用的输出，备份 XML，并加入 J71b 的原生触摸输出映射；随后重载登录配置，按型号、驱动和固件名检查后重新初始化触摸控制器。
7. 用户通过正常 PIN 登录进入新桌面；再次在本机解锁，并拖动新开的测试终端标题栏，明确确认窗口已能正常移动。

当前桌面仍为 `mouseEmulation="no"`、原有输出映射和单位校准矩阵。没有留下失败的标题栏按下移动绑定，也没有新增自动重启桌面或重置控制器的服务。

**这次恢复包含桌面会话重建、登录触摸映射补齐及控制器重新初始化，未单独验证哪一项起决定作用。** 不能把它当成 PR #52 已验证自动恢复的证据，也不能据此宣称长期拖动问题已永久修复。登录配置的修复目前应用于这台 J71b，不把它的输出名硬编码成其他机型的中文默认配置。操作记录、公开代码和个人认证数据继续分开保管。

## 11. 物理按键触摸恢复入口（2026-11-02）

用户要求同时按 Home 和音量加，自动执行上述已奏效的恢复步骤。新增 [Home＋音量加恢复快捷键](touch-recovery.md)：按住 3 秒触发，关闭当前应用并回到正常 PIN 登录界面；每次完整按下、松开只触发一次，冷却 30 秒。仅在 J71b 上启动，不定时重置，不绕过登录。

本机安装时，普通账户先备份、更新 `omarchy-tablet-power` 和亮度命令，并补装音量命令。旧版系统的音量键原本调整亮度，因此相对亮度调整也加入了组合键抑制；单键用途保留。用户在 Mac 终端隐藏输入 Linux 账户密码后，安装器校验代码摘要、型号、显示面板及 GPIO 按键，安装 root 管理的恢复工具和 systemd 服务。`systemd-analyze verify` 通过，服务已设为开机启动，日志显示 `Home + Volume Up recovery ready`。没有新增免密码 sudo，也未替换磁盘上的内核模块。

本地全量测试为 128 项，结果通过、18 项因环境条件跳过；随后新增并通过登录配置权限回归测试。新增专项测试覆盖组合键、冷却、丢事件后的重新按键、配置备份与符号链接拒绝，以及事件监听器。镜像打包测试包含服务和工具，尚未构建、安装新的完整镜像。

[GitHub 检查](https://github.com/jarodlee/omarchy-a/actions/runs/41419074412)在 Python 3.11 和 3.14 上均通过，共 129 项；期间补齐上游新增 ARMv7 手动固件清单的读取，继续排除复制文件、生成固件和机主校准数据，未知清单仍拒绝审计。

实体测试最初没有切换桌面。后续日志确认组合键已触发，但登录目录为 `775`、配置为 `664`，因此工具因允许组写入而拒绝继续；当时并未关闭桌面。用户在 Mac 终端隐藏输入 Linux 账户密码后，将 root 管理的登录目录改为 `755`、配置改为 `644`。打包代码同步规范 greeter 权限，覆盖从宽松权限的开发机复制文件的情况，保留恢复工具的原有安全检查。

修正后，用户再次按住 Home＋音量加，日志确认从实体组合键触发到 `Recovery exit: 0` 约 5 秒，桌面进程确已重建；用户正常 PIN 登录，确认点击及标题栏拖动均正常。服务仍运行、已启用开机启动，尚未另外执行冷启动实测。此结果验证了应急入口，不代表触摸长期故障根因已经消除。

安装期间墙充限流再次回落，电量读数到 0%。用户保持息屏并重新插接后，驱动重新识别 `BrickID`、允许 2.4 A，电池净充入约 1.6–1.7 A，读数随后回升。仍未强写充电限流或绕过保护；本功能不处理充电故障。
