# 设备运行与电池的 24 小时统计

入口：https://ipad.lxj.ai/battery/，本机原端口 3001 也可使用。
在已有 Python 电池服务中扩展，没有增加常驻服务、第三方 Python 包或图表库。

## 指标与采样

- 整机 CPU 使用率（全部核心合计满载为 100%）、1/5 分钟负载及连续运行时间。
- 内存总量、可用量和已用量，Swap 总量与已用量；已用内存按 `MemTotal - MemAvailable` 计算。
- Linux 根分区容量、已用/可用空间及该分区的磁盘读写速率。
- 活动物理网卡的接收/发送速率与所选时间范围累计流量，不重复累计回环、VPN 等虚拟接口。
- 原有电量、净电流、温度、电压和输入限流。

只读取内核与 power_supply 计数器，不发测速流量，不采集进程列表、IP、连接目的地或学习记录。
CPU 不重复计算 guest 字段；磁盘 sector 按内核规定的 512 字节单位转换。
内核字段依据：[proc 文档](https://www.kernel.org/doc/html/latest/filesystems/proc.html)、
[I/O 统计文档](https://www.kernel.org/doc/html/latest/admin-guide/iostats.html)。

每分钟保存一次原始采样。新增 `system_samples` 表滚动保留 24 小时，
原 `samples` 电池表继续保留七天；升级是增加表，未清空原有电池历史。
升级前的在线数据库备份位于设备私有维护目录 `battery-before-system.sqlite3`，不进入 Git。
采样线程复用自己的 SQLite 连接，每次采样仍单独提交事务，避免每分钟关闭连接都触发检查点。
HTTP 请求的短连接会及时关闭。跨连接已提交可见性有回归测试。

重启、计数器回退、网卡变化和超过 150 秒的缺测不计作虚假速率峰值。
累计网络/磁盘字节只计算同一次启动、计数器持续有效的连续采样段，页面显示其有效覆盖时间。
历史空白不补零；首次启用无法还原过去的系统数据，需要逐步积累。

## 页面与请求开销

默认最近 24 小时，可切换 1/6/24 小时。
当前状态每 20 秒请求 `/api/battery?view=current`，该响应不查询或返回历史。
历史每五分钟或用户手动刷新/切换范围时请求 `/api/battery?hours=24`。
后台标签页暂停刷新；返回前台取得新状态。服务端当前读数缓存五秒，历史缓存最多一分钟，
新增采样会使历史缓存失效。

24 小时展示按四分钟汇总，通常为 360 点；重启等边界可以额外分段。
CPU 峰值及内存峰值仍从原始每分钟数据统计，CPU 采样本身是区间均值，不是瞬时峰值。
图表在访问者浏览器绘制；每五分钟才重绘历史，窗口缩放使用已有数据重排。
390px 手机布局已实测无横向溢出，包含运行状态/历史/电池的快速跳转。

首页的只读电池代理已支持 `view=current` 和限定的 `hours`，继续限制固定目标与最大响应大小，
不提供任意 URL 代理。页面未增加充电控制或驱动写入。

## iPad 实测与容量基准

测试设备为 J71b / A10 双核、约 2GB 内存，仍保留原服务的 64MiB 内存和 10% 单核 CPU 配额。
测量摘要在 `system-monitor-performance.json`，可复用 `measure-monitor-idle.sh` 与 `benchmark-monitor.sh`。

| 项目 | 结果与口径 |
| --- | --- |
| 升级后 60 秒 cgroup CPU 观察 | 0.094222 CPU 秒，约 0.157% 单核；不是页面上整机 CPU 百分比 |
| 该窗口主进程 RSS | 30638080 字节，约 29.2MiB，包含共享页 |
| 采样与写入的一次 CPU 时间 | 临时库基准均值约 16.3ms；每分钟一次折算约 0.027% 单核，不含网页访问 |
| 一次采样与写入的墙钟时间 | 约 129ms，包含传感器和 I/O 等待，不等于 CPU 忙碌时间 |
| 未命中缓存的完整 24h 历史查询 | 1440 行临时数据，CPU 均值约 41.8ms；页面五分钟请求一次 |
| 1440 行系统历史的主库增量 | 245760 字节，240KiB；不含原电池表、WAL 和检查点文件 |
| 24h 完整 JSON 基准 | 约 150KiB；当前状态小报文实测约 0.8–1KiB |

按未压缩 JSON 和前台连续打开计算，页面数据流量约 2–3MiB/小时，实际还受 HTTP 压缩影响。
基准数据较规则，其 gzip 大小不能代表真实网络流量。
SQLite WAL/检查点会额外占用空间，一般为数 MiB；240KiB 不是整个服务的总磁盘占用。
短基准的进程 `write_bytes` 约 29KiB/次，包含电池与系统写入，不是闪存物理写入量，
也未覆盖所有周期检查点，不能据此推算闪存寿命。

这是单机短观察和临时 1440 行基准，不是全天持续测量或多人压力测试。
旧版另一次 60 秒观察约 0.137% 单核，但两个窗口的访问和进程运行时长不同，
不把差值当作严格的升级增量，也不把刚重启后的 RSS 当作长期上限。
访问人数、请求频率和系统负载变化会改变开销。

## 安装、验证与回退

将 `battery-monitor.py`、`system_telemetry.py`、`index.html` 放在 `/opt/ipad-battery-monitor/`，
应用文件由 root 持有、服务用户只读；保留原 state 目录与 unit，重启 `ipad-battery-monitor`。
同时更新首页 `omarchy-home.py` 以接受小报文查询，再重启首页服务。

- `check-monitor.py`：有符号电流、缺失传感器及七天电池清理通过。
- `test_system_telemetry.py`：CPU/内存/字节单位、计数器回退、峰值/断点、累计量、
  24 小时系统清理、旧电池保留、跨连接提交、轻量接口不读取历史通过。
- 公网浏览器已显示八张图，默认范围为 24 小时；原电池数据正常显示。
- 24h 容量和查询基准只使用自动清理的临时数据库，没有向真实历史写入虚构采样。

回退可从旧提交恢复原电池脚本和页面。新增表不妨碍旧代码读取电池表，
通常无需替换数据库；回退前仍应备份实时数据库。不要把新系统表复制成伪造的既往历史。
本功能仍是可选部署，CHANGELOG 未修改。拟议说明：轻量设备监测新增 CPU、内存、
磁盘与网络的 24 小时统计，并降低历史请求与重绘频率。
